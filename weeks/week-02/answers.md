# Ответы

### 1. Чем `PUT` принципиально отличается от `PATCH`? Какой из них является идемпотентным?
*   **PUT** — используется для **полной замены** ресурса. Вы должны отправить все поля объекта. Если каких-то полей не будет в запросе, они могут быть затерты или установлены в `null`.
*   **PATCH** — используется для **частичного обновления** ресурса. Вы отправляете только те поля, которые хотите изменить.
*   **Идемпотентность:** 
    *   **PUT** — идемпотентен. Многократное повторение одного и того же запроса приведет к одному и тому же результату.
    *   **PATCH** — формально *не всегда* идемпотентен (хотя на практике часто бывает таким). Если логика PATCH подразумевает, например, добавление элемента в список, то повторный запрос добавит элемент еще раз.

### 2. HTTP коды ошибок
*   **400 (Bad Request) vs 422 (Unprocessable Entity):**
    *   **400:** Ошибка синтаксиса запроса (например, битый JSON или неверный тип данных).
    *   **422:** Синтаксис верный, но данные не проходят бизнес-валидацию (например, дата рождения в будущем или логин уже занят).
*   **401 (Unauthorized) vs 403 (Forbidden):**
    *   **401:** Пользователь не аутентифицирован (система не знает, кто это). Требуется войти в систему.
    *   **403:** Пользователь известен, но у него **недостаточно прав** для доступа к этому конкретному ресурсу.
*   **404 (Not Found):**
    *   Ресурс по указанному адресу не существует.

### 3. Зачем нужны негативные тесты (тесты на ошибки)?
Они проверяют устойчивость системы. Важно убедиться, что:
*   Приложение не "падает" при получении некорректных данных.
*   Система возвращает понятные сообщения об ошибках, а не "500 Internal Server Error".
*   Безопасность соблюдена (например, нельзя получить доступ к чужим данным).
*   Машина состояний не позволяет совершать запрещенные переходы.

### 4. Почему важно возвращать ошибки в структурированном формате (JSON)?
*   **Машиночитаемость:** Фронтенд или другой микросервис может легко распарсить JSON и подсветить конкретное поле с ошибкой в интерфейсе.
*   **Стандартизация:** Позволяет передавать не только текст, но и коды ошибок, которые легко локализовать (перевести на разные языки) на стороне клиента.
*   **Информативность:** Можно передать массив из нескольких ошибок сразу, а не одну строку.

### 5. Что такое "обратная совместимость" API и роль валидации?
*   **Обратная совместимость** — это способность новой версии API работать со старыми клиентами без внесения изменений на их стороне.
*   **Валидация и совместимость:**
    *   **Помогает:** Строгая валидация на входе гарантирует, что в систему не попадут данные, которые "сломают" старую логику.
    *   **Мешает:** Если добавить новое обязательное поле (Required) и включить на него жесткую валидацию, старые клиенты, которые про это поле не знают, перестанут работать. Поэтому для сохранения совместимости новые поля обычно делают необязательными.
